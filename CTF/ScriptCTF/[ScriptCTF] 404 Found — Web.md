

**카테고리**: Web **힌트**: "Please don't hack my shopping cart!"

Lumina라는 가짜 로봇 쇼핑몰이 주어지는 문제였다. 힌트 문구가 너무 노골적이어서 처음엔 당연히 장바구니 로직 자체를 뜯어야 하는 문제인 줄 알았는데, 결과적으로는 완전히 다른 곳에 답이 있었다.

---

## 사용 도구

- Burp Suite (Proxy / Repeater)
- 브라우저 개발자도구
- `flask-unsign` (Flask 세션 쿠키 크래킹용)

## 사이트 구조 파악

Flask로 만든 SPA에 가까운 쇼핑몰이었다. 
`/shop`, `/cart`, `/checkout` 같은 페이지는 정적 HTML이 아니라 JS가 뜨자마자 내부 API를 호출해서 채워 넣는 방식이었고, 페이지 소스를 열어보면 아래 API들이 있었다.

- `GET /api/products`
- `POST /api/cart`, `PUT /api/cart/<id>`, `DELETE /api/cart/<id>`
- `POST /api/promo`
- `POST /api/checkout`
- `POST /api/reviews`
- `POST /api/login`, `/api/register`, `/api/logout`
- `POST /api/newsletter`

장바구니 상태는 서버 DB가 아니라 **Flask 세션 쿠키(itsdangerous 서명)** 안에 그대로 들어있었다. 쿠키를 base64 디코딩해보면 `{"cart": {"3": 1}}` 이런 식으로 평문 JSON이 보인다. 서명만 없으면 누구나 고쳐 쓸 수 있는 구조라서, 처음엔 "이거다" 싶었다.

## Fail Point 1 — 장바구니 "해킹"하려던 시도들

힌트가 "장바구니를 해킹하지 마세요"였으니 자연스럽게 가격/수량 조작 쪽을 먼저 팠다.

**1) 수량 음수 넣기** `PUT /api/cart/<id>`에 `{"qty": -50}`을 보내봤다. 서버가 `max(0, qty)`로 클램프하고 있어서 그냥 항목이 삭제되는 걸로 끝났다. `POST`로 새 상품을 담을 때도 마찬가지로 음수는 자동으로 1로 고정됐다.

**2) 타입 조작** `qty`에 문자열, `null`, `true` 같은 값을 넣어봤다. `null`이나 `true`는 500 에러가 났지만 디버그 모드가 꺼져 있어서 스택트레이스 노출은 없었고, 문자열(`"abc"`)은 그냥 무시되고 기존 값이 유지됐다. 타입 체크가 생각보다 꼼꼼했다.

**3) 프로모 코드 중복 적용** `WELCOME10`을 여러 번 연속으로 적용해봤다. 할인액이 세션에 누적 저장되는 게 아니라 **요청마다 subtotal의 10%를 실시간 재계산**하는 구조라, 몇 번을 눌러도 할인율이 고정이었다. 다른 코드 이름도 사전식으로 여러 개 찔러봤지만 전부 `"That code isn't valid."`.

**4) checkout 단계에서 mass assignment 시도** `POST /api/checkout` 요청 바디에 폼에 없는 필드(`total`, `subtotal`, `discount`, `price`)를 몰래 끼워 넣어봤다. 서버가 정직하게 서버 계산값으로 덮어써서 무시당했다. (오히려 정상 결제가 실제로 체결되면서 장바구니가 비워지는 부작용만 있었다.)

**5) 세션 쿠키 시크릿 키 크래킹** 쿠키가 클라이언트에 그대로 노출된 구조라, `flask-unsign`으로 서명 키(SECRET_KEY) 브루트포스를 시도했다. 유출된 시크릿 모음 사전(5~6만 단어)과 챌린지 테마 관련 커스텀 워드리스트까지 돌려봤지만 실패.

**6) 리뷰 폼 SSTI / XSS** 상품 페이지의 리뷰 작성 폼은 사용자 입력이 그대로 저장되고 재렌더링되는 지점이라 고전적인 취약점 후보였다. `{{7*7}}`을 넣어봤지만 계산되지 않고 텍스트 그대로 출력(SSTI 아님), `<img src=x onerror=alert(1)>` 같은 태그도 이스케이프되어 그냥 문자열로 찍혔다(XSS도 아님).

여기까지 오면서 든 생각: **가격/할인 계산 로직은 거의 방어가 완벽했다.** 서버가 클라이언트 입력을 신뢰하지 않고 매번 재계산하는 구조라, "장바구니 자체를 해킹"하는 정공법은 답이 아니었던 것 같다.

## 전환점



> **404 Found**

"404 Not Found"가 아니라 **Not이 빠진 404 Found**. 이게 진짜 힌트였다. 힌트 문구("장바구니를 해킹하지 마세요")는 낚시였고, 찾아지면 안 되는 페이지를 찾기 위해 재접근 시도했다.


- `robots.txt` (크롤러에게 "색인하지 마" 라고 알려주는 파일)
- `sitemap.xml`
- HTML 소스 안 주석
- JS 번들 안에 죽은 코드/주석

이 중 확인 비용이 제일 싸고, 개념적으로 제목이랑 제일 딱 맞아떨어지는 게 `robots.txt`였다. 


---

## 풀이

`/robots.txt` 접속.

```
User-agent: *
Disallow: /the-best-robot
```

바로 `/the-best-robot` 경로로 들어가니 플래그가 있었다.

```
ScriptCTF{r0b07s_4r3_t4k1ng_0v3r_fa648bf8dc0f}
```
