
## 분석에 쓰는 도구와 이벤트 ID

| 도구                    | 용도                                                                 |
| --------------------- | ------------------------------------------------------------------ |
| **이벤트 뷰어** (eventvwr) | `.evtx` 로그 파일을 열어 이벤트 하나하나를 상세 확인                                  |
| **Sysmon**            | 기본 로그보다 훨씬 자세하게 프로세스 실행·네트워크 연결·파일 생성을 기록하는 MS 공식 도구               |
| **Hayabusa**          | 여러 `.evtx`를 한 번에 스캔해서 Sigma 룰로 의심 이벤트를 골라 **타임라인(CSV)** 으로 뽑아주는 도구 |


**자주 보는 이벤트 ID**

| 로그          | ID       | 의미                                   |
| ----------- | -------- | ------------------------------------ |
| Sysmon      | 1        | 프로세스 생성 (CommandLine, 부모 프로세스 확인 가능) |
| Sysmon      | 3        | 네트워크 연결                              |
| Sysmon      | 7        | 이미지(DLL) 로드                          |
| Sysmon      | 11       | 파일 생성                                |
| Application | 1000     | 응용 프로그램 오류 (프로그램 비정상 종료)             |
| Application | 1002     | 응용 프로그램 응답 없음 (Hang)                 |
| Application | 22 (VSS) | 볼륨 섀도 복사본 서비스 오류                     |
| System      | 7045     | **새 서비스 설치**                         |
| System      | 7036     | 서비스 상태 변경 (실행 중 / 중지)                |
| System      | 7009     | 서비스 시작 시간 초과                         |
|             |          |                                      |

💡 **분석 원칙**

- 이벤트 ID **하나만으로 악성이라고 단정하지 않는다.** 프로세스 실행, 네트워크 연결, 서비스 설치, 파일 생성 같은 **서로 독립적인 증거를 시간 순서(Timestamp)로 연결**해서 결론을 낸다.
- Sysmon의 `UtcTime`은 **UTC 기준**이다. 한국 시간(KST)은 **+9시간** 해서 본다. 이벤트 뷰어 목록의 시간은 PC 시간대 기준이라 서로 다르게 보일 수 있다.

**분석**

- 파일 이름은 `winpm.exe`인데 설명(Description)은 **Console Based Script Host** → 원래 `cscript.exe`(윈도우 스크립트 실행기)를 **이름만 바꿔서** `C:\ProgramData`에 숨겨둔 것
- `//e:{CLSID}` 옵션으로 스크립트 엔진을 이름이 아닌 **CLSID(고유 ID)로 지정**해 `jscript9.dll` 엔진으로 `winpm_update.js`를 실행
- 결과적으로 "cscript.exe가 JS를 실행했다"는 흔한 탐지 룰을 피해 간다

> 📝 **탐지 포인트** : 파일명과 Description / Product가 맞지 않는 프로세스, `C:\ProgramData`처럼 실행 파일이 있을 이유가 없는 경로에서 실행된 프로세스
regsvr32.exe를 실행하여 외부 링크(github)에서 calc.sct 파일을 다운로드 받아옴

|옵션|의미|
|---|---|

|`/u`|등록 해제 모드 (실제 DLL 등록 없이 동작)|

|`scrobj.dll`|받아온 `.sct` 안의 스크립트를 실행해주는 DLL|

**분석**

- 정상 윈도우 프로그램인 `regsvr32.exe`로 **외부(GitHub)의 스크립트를 내려받아 바로 실행** → 전형적인 **Squiblydoo** 우회 기법
- 서명된 MS 프로그램이 실행하는 것이라 화이트리스트(AppLocker 등)를 우회하고, 파일이 디스크에 남지 않는다
- 이번 샘플의 `calc.sct`는 계산기를 띄우는 **PoC(개념 증명)** 파일이지만, 실제 공격에서는 이 자리에 악성 스크립트가 들어간다
- 실제 payload 다운로드 여부는 같은 시간대의 **네트워크 연결(Sysmon 3)** 로그를 함께 보면 증적으로 확인할 수 있다

서비스 실행 명령이 일반적인 Windows 시스템 경로가 아닌 C\ProgramData\ 아래에 이상한 파일을 가리키고 있음, 또한 서비스의 이름이 Windows 보안 센터 서비스와 혼동을 줄 수 있는 이름으로 위장할 수 있는 상태로 보임.

의심스러운 경로나 서비스 이름을 의심하는건 좋지만, 경로 or 파일명만으로 악성이라고 단정하는 것은 섣부른 판단일 수 있음.
파일 해시, 서명, 생성 시간, 프로세스 실행 흔적 등 다양한 증적을 보고 판단해야함.

그리고 이벤트 ID로 보고 싶다 7045(새 서비스 설치), 7036(서비스가 실행 중/ 중지 상태로 전환)

- 이벤트 로그 시간은 시스템의 시간대 설정에 따라 표시가 달라질 수 있음
- 
- 이벤트 ID 하나만으로 악성 여부를 판단하면 안된다. 프로세스 간 충돌, 서비스 설치 및 실행, 파일 생성 및 암호화 흔적 등 서로 독립적인 증거를 시간순서(TimeStamp) 기반으로 연결해서 결론을 내려야 한다.
