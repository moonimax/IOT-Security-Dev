#  코드 변환

## 빌드 과정

### Java/Kotlin -> .class -> .dex

안드로이드(Android)는 스마트폰과 태블릿에서 동작하는 운영체제다.

```
1. .java, .kt
   ↓
2. Java byte 코드 (d8, dx) 변환
   ↓
3. Dex 바이트코드 (.dex)
   ↓ ART에서 실행 / dex2oat
4. OAT 파일(.oat) 
   ↓ 
5. 실행   
```

**단계별 특징**
- 개발자 작성하여 사람이 읽을 수 있는 소스코드
- JVM 바이트코드(스택 기반)
- 안드로이드 바이트코드(레지스터 기반)



### Java vs 안드로이드 빌드 차이

| 구분    | JAVA       | 안드로이드      |
| ----- | ---------- | ---------- |
| 바이트코드 | Java 바이트코드 | Dex -> OAT |
| VM    | Java VM    | ART        |
| 컴파일   | JIT        | AOT + JIT  |
| 실행 속도 | 보통         | 빠름         |



## 1. Smali 코드

### 오픈소스 특징

**Smali** 는 DEX 바이트코드를 사람이 읽을 수 있는 형태로 변환
- smali 파일은 코드를 열어 게임 내 데이터 값을 변조하거나 다른것들을 할 수 있음
- 역어셈블(basksmali) - JAVA의 소스 코드 디컴파일


```
Java / Kotlin source code
   ↓
Dex bytecode
   ↓ dassemble (baksmali)
Smali code
```


### Smali 기본 문법 - Java 타입 매핑

|Java 타입|Smali 표기|
|---|---|
|`void`|`V`|
|`int`|`I`|
|`boolean`|`Z`|
|`String`|`Ljava/lang/String;`|
|`int[]`|`[I`|

**Smali 코드 분석**
- 앱 로직 파악
- 보안 검증 우회
- 라이선스 체크 우회
- 중요 로직 추출


**리패키징 과정**
```
// APK 디컴파일
apktool d <APK.name>

// Smali 코드 수정
vi MyApp/smali/.../MainActivity.smali

// Rebuilding
apktool b <복사 APK>/ -o my.keystore <생성 APK name>.apk

// install
adb install <APK.name>
```

## 2. JNI란

**JNI (Java Native Interface)**: Java/Kotlin 코드와 C/C++ 네이티브 코드를 연결하는 인터페이스


**파일 위치**
-  시스템 라이브러리 /system/
- 개별 apk 안에 들어있음


### 2.1 JNI 동작 방식


```kotlin
// 1. Java/Kotlin에서 native 메서드 선언
external fun calculate(): Int

// 2. System.loadLibrary()로 .so 파일 로드
System.loadLibrary("native-lib")

// 3. JNI를 통해 C/C++ 함수 호출
val result = calculate()

// 4. C/C++ 함수 실행 후 결과 반환
return 42
```

## 4. 보안 관점 - 리버싱 난이도


#### 리버싱 난이도 순서 [쉬움] → [어려움]

1. **Java/Kotlin (DEX)** — JADX로 디컴파일 → 거의 원본 소스코드
2. **Smali** — 사람이 읽을 수 있는 어셈블리
3. **C/C++ (.so)** — IDA/Ghidra로 디스어셈블 → 어셈블리만 보임



**취약한 방법 (Java/Kotlin) — 하드코딩:**



```kotlin
// MainActivity.kt
fun checkLicense(): Boolean {
    val licenseKey = "ABC123XYZ"  // 하드코딩된 라이선스 키
    return userInput == licenseKey
}
// 문제점: JADX로 디컴파일 시 licenseKey가 그대로 노출 → 쉽게 우회 가능
```

**보안 강화 방법 (C/C++) — 네이티브로 이동:**



```cpp
// native-lib.cpp
extern "C" JNIEXPORT jboolean JNICALL
Java_com_example_MainActivity_checkLicense(
    JNIEnv* env, jobject, jstring input) {
    // 복잡한 암호화 알고리즘
    // 라이선스 키가 기계어로 숨겨짐
    // 리버싱 매우 어려움
    return JNI_TRUE;
}
```

**네이티브 코드 보안 장점**: 중요한 알고리즘 숨김 · 암호화 키 보호 · 라이선스 체크 로직 보호 · 디컴파일 거의 불가능

## 5. Java API Framework

Java API Framework는 앱이 시스템 기능을 **안전하고 정해진 방법**으로 쓸 수 있게 해주는 공식 도구 모음이다. 안드로이드에서는 각 앱이 **독립된 공간**에서 실행되므로 다른 앱/시스템 내부에 함부로 접근할 수 없다. 그래서 데이터 공유, 기능 호출, 시스템 자원(카메라, 위치 등) 사용은 반드시 **Framework가 제공하는 정해진 통로(API)** 를 거쳐야 한다.


### Framework의 위치 (안드로이드 스택)

```
┌────────────────────────────┐
│  Applications (앱)          │
├────────────────────────────┤
│  Java API Framework ← 여기! │
├────────────────────────────┤
│  Android Runtime | Native Libraries │
├────────────────────────────┤
│  HAL                        │
├────────────────────────────┤
│  Linux Kernel                │
└────────────────────────────┘
```

## 6. Content Provider 보안


Permission으로 Content Provider 접근을 세밀하게 제어할 수 있다.

### 권한 속성 비교

|속성|적용 범위|설명|
|---|---|---|
|`android:permission`|읽기 + 쓰기 모두|하나의 권한으로 읽기/쓰기 모두 제어|
|`android:readPermission`|읽기만|데이터 조회(query)에만 적용|
|`android:writePermission`|쓰기만|삽입/수정/삭제(insert/update/delete)에만 적용|


### 설정 방법 1 - 통합 권한


```xml
<!-- 1단계: 임의의 커스텀 권한 "com.example.provider.permission.ACCESS_PROVIDER" 정의 -->
<!-- android:protectionLevel: signature로 설정하여 동일 서명 앱만 허용 -->
<permission
    android:name="com.example.provider.permission.ACCESS_PROVIDER"
    android:protectionLevel="signature" />

<!-- 2단계: Provider에 권한 적용 -->
<provider
    android:name=".MyProvider"
    android:authorities="com.example.provider"
    android:exported="true"
    android:permission="com.example.provider.permission.ACCESS_PROVIDER" />
```

**결과**: 읽기/쓰기를 하려면 접근 앱이 `ACCESS_PROVIDER` 커스텀 권한을 갖고 있어야 하며, `protectionLevel="signature"`이므로 **동일 서명 앱**이어야 한다.


### 설정 방법 2 - 읽기/쓰기 분리


```xml
<!-- 읽기 권한 정의 -->
<permission
    android:name="com.example.provider.permission.READ_PROVIDER"
    android:protectionLevel="signature" />

<!-- 쓰기 권한 정의 -->
<permission
    android:name="com.example.provider.permission.WRITE_PROVIDER"
    android:protectionLevel="signature" />

<!-- Provider에 적용 -->
<provider
    android:name=".MyProvider"
    android:authorities="com.example.provider"
    android:exported="true"
    android:readPermission="com.example.provider.permission.READ_PROVIDER"
    android:writePermission="com.example.provider.permission.WRITE_PROVIDER" />
```


**결과**: 읽기와 쓰기를 별도로 제어 가능. `READ_PROVIDER`, `WRITE_PROVIDER` 권한을 **둘 다 가진 앱만** 읽기/쓰기 모두 가능. 마찬가지로 `signature`이므로 동일 서명 앱이어야 함.



### Permission protectionLevel


어떤 커스텀 권한의 `protectionLevel`은 **가장 먼저 설치한 앱**에서 결정된다. 만약 악성앱이 시스템/기본 앱보다 먼저 설치되어 있다면 임의의 커스텀 권한을 `normal`로 선점할 수 있지만, 실제로 악성앱이 시스템·기본 앱보다 먼저 설치되어 있는 경우는 흔치 않다.


|Level|설명|보안 수준|
|---|---|---|
|`normal`|단순 기능 식별 (사용자 동의 불필요)|낮음 (취약)|
|`dangerous`|민감한 정보 접근 (사용자 동의 필요)|중간 (취약)|
|`signature`|동일한 서명의 앱만 허용|높음 (안전)|
|`signatureOrSystem`|시스템 앱 또는 동일 서명|매우 높음 (안전)|




### 보안 취약점 주의 - 한쪽 권한 누락



```xml
<!-- BAD: 쓰기 권한 없음 → 누구나 데이터 수정 가능 -->
<provider
    android:readPermission="com.example.permission.READ_PROVIDER" />
```

> [!danger] 흔한 실수 `readPermission`만 설정하고 `writePermission`을 빠뜨리면, **읽기는 막혀도 쓰기(삽입/수정/삭제)는 누구나 가능**한 상태가 된다. 읽기/쓰기를 분리해서 설정할 땐 반드시 **양쪽 다** 지정했는지 확인해야 한다.
