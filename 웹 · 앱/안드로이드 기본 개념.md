# 1. 안드로이드 기본 개념

## 1.1 안드로이드란?

### 리눅스 기반 모바일 운영체제

안드로이드(Android)는 스마트폰과 태블릿에서 동작하는 운영체제다.

**핵심 특징**
- 리눅스 커널을 기반으로 제작한다.
- 구글이 개발 및 배포한다.
- 전 세계 스마트폰의 약 70% 이상을 점유한다.

**리눅스 기반의 의미**

| 리눅스 기능  | 안드로이드 활용           |
| ------- | ------------------ |
| 파일 시스템  | 앱 데이터 저장, 파일 권한 관리 |
| 프로세스 관리 | 여러 앱 동시 실행         |
| 메모리 관리  | RAM 할당 및 회수        |
| 보안      | 앱별 UID 격리          |

### 오픈소스 특징

**AOSP (Android Open Source Project)**
- 누구나 소스코드를 확인할 수 있다.
- 제조사별 커스터마이징이 가능하다 (삼성 One UI, LG UX 등).
- 개발자 커뮤니티 참여가 가능하다.

**오픈소스의 장점**
- 투명성: 코드 검증이 가능하다.
- 확장성: 다양한 기기에 적용한다.
- 커뮤니티: 빠른 버그 수정이 이루어진다.

**오픈소스의 단점**
- 분편화: 제조사마다 버전이 다르다.
- 업데이트 지연: 통일된 업데이트가 어렵다.

## 1.2 안드로이드 계층 구조

### 5개 계층 개요

안드로이드는 5개의 계층으로 구성된다.

```
┌──────────────────────────────┐
│      Applications             │  5층
├──────────────────────────────┤
│    Java API Framework         │  4층
├──────────────────────────────┤
│ Android Runtime | Native Libs │  3층
├──────────────────────────────┤
│   HAL (Hardware Abstraction)  │  2층
├──────────────────────────────┤
│        Linux Kernel           │  1층
└──────────────────────────────┘
```

### 각 계층의 역할

**1층: Linux Kernel**
- 역할: 하드웨어를 직접 제어한다.
- 기능: CPU, 메모리, 프로세스, 파일 시스템을 관리한다.
- 보안: 앱별 UID 격리, SELinux를 적용한다.

**2층: HAL (Hardware Abstraction Layer)**
- 역할: 하드웨어를 추상화한다.
- 기능: 제조사별 하드웨어 차이를 숨긴다.
- 예시: 삼성/LG 카메라 → 통일된 "Camera" 인터페이스로 접근한다 (실제 하드웨어 차이는 무시하고 "Camera"에만 접근하면 된다).

**3층: Android Runtime + Native Libraries**
- Android Runtime (ART): Java/Kotlin 코드를 실행한다.
- Native Libraries: C/C++ 고성능 라이브러리다.
- 예시: Webkit(웹), OpenGL(3D), SQLite(DB)

**4층: Java API Framework**
- 역할: 앱이 시스템 기능을 사용하거나 다른 앱과 상호작용할 때 사용한다 (앱은 서로 독립적이고 상호 접근 권한이 없기 때문에 Java API Framework를 통해 하나의 앱이 다른 앱이나 시스템에 접근할 수 있다).
- 제공: Content Provider, View System, System Manager
- 기능: 카메라, GPS, 알림, 전화 등을 지원한다.

**5층: Applications**
- 역할: 사용자 앱이다.
- 언어: Java/Kotlin
- 예시: 카카오톡, 인스타그램, 게임

## 1.3 APK 구조

### APK 파일 구성 요소

APK (Android Package Kit)는 안드로이드 앱의 설치 파일이다.
- 실제로는 ZIP 압축 파일이다.
- 압축을 해제하면 내부 구조를 확인할 수 있다.

**APK 내부 구조**

```
MyApp.apk
├── AndroidManifest.xml    (앱 설정 파일)
├── classes.dex            (실행 코드)
├── resources.arsc         (리소스 테이블: res/의 메타 정보, 소수의 리소스 데이터)
├── res/                   (리소스: 리소스 데이터 저장)
│   ├── layout/            (화면 레이아웃)
│   ├── drawable/          (이미지)
│   └── values/            (문자열, 색상)
├── lib/                   (네이티브 라이브러리)
|   ├── arm64-v8a/         (.so 파일)
│   └── armeabi-v7a/
├── assets/                (추가 파일)
└── META-INF/              (서명 정보)
```

**파일별 역할**

| 파일/폴더               | 역할         | 설명                      |
| ------------------- | ---------- | ----------------------- |
| AndroidManifest.xml | 앱 설정       | 권한, 컴포넌트, 앱 이름 등        |
| classes.dex         | 실행 코드      | Java/Kotlin → DEX 바이트코드 |
| res/                | 리소스        | 이미지, 레이아웃, 문자열 등        |
| lib/                | 네이티브 라이브러리 | C/C++ .so 파일            |
| assets/             | 추가 파일      | 폰트, 데이터 파일 등            |
| META-INF/           | 서명         | 앱 무결성 검증                |
| XML/                | 앱 설정 파일    | 앱 무결성 검증                |


### AndroidManifest.xml 역할

AndroidManifest.xml은 앱의 설정 파일이다.

**주요 내용**

```xml
<manifest>
    <!-- 앱 패키지명 -->
    <package="com.example.myapp" />

    <!-- 권한 요청 -->
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.CAMERA" />

    <application>
        <!-- Activity 등록 -->
        <activity android:name=".MainActivity"
                  android:exported="true" />  <!-- 외부 앱에서 컴포넌트 호출 허용 -->

        <!-- Service 등록 -->
        <service android:name=".MusicService" />

        <!-- Broadcast Receiver 등록 -->
        <receiver android:name=".AlarmReceiver" />

        <!-- Content Provider 등록 -->
        <provider android:name=".MyProvider" />
    </application>
</manifest>
```

### 모의해킹 관점

- AndroidManifest.xml을 분석하면 앱 구조를 파악할 수 있다.
- `exported="true"` 설정은 취약점으로 이어질 수 있다.
- 불필요한 권한 요청은 보안 문제로 이어진다.

# 2. 안드로이드 4대 컴포넌트

## 2.1 컴포넌트 개념

### 컴포넌트란?

컴포넌트(Component)는 안드로이드 앱을 구성하는 특별한 Java/Kotlin 클래스다.

**핵심 정의**
- APK 안에 있는 특별한 코드 조각이다.
- Java/Kotlin으로 작성된 클래스다.
- 특정 부모 클래스를 상속받아 만든다.
- 시스템이 생명주기를 관리한다.

**4대 컴포넌트**

| 컴포넌트               | 상속 클래스                 | 역할       | 예시        |
| ------------------ | ---------------------- | -------- | --------- |
| Activity           | `Activity` 상속          | 화면(UI)   | 로그인 화면    |
| Service            | `Service` 상속           | 백그라운드 작업 | 음악 재생     |
| Broadcast Receiver | `BroadcastReceiver` 상속 | 이벤트 수신   | 배터리 부족 알림 |
| Content Provider   | `ContentProvider` 상속   | 데이터 공유   | 연락처 공유    |

**컴포넌트 클래스 예시**

```kotlin
// Activity 컴포넌트
class MainActivity : AppCompatActivity() {
    // Activity 클래스를 상속받음
}

// Service 컴포넌트
class MusicService : Service() {
    // Service 클래스를 상속받음
}
```

### 시스템 관리 vs 일반 코드

**일반 코드 (Utils, Helper 등)**
- 개발자가 직접 생성한다 (`new` 키워드).
- 개발자가 생명주기를 관리한다.
- AndroidManifest.xml 등록이 불필요하다.

**컴포넌트 (Activity, Service 등)**
- 시스템이 생성하고 관리한다.
- 시스템이 생명주기를 관리한다.
- Intent로 시스템에 요청해야 실행된다.
- AndroidManifest.xml에 반드시 등록해야 한다.

**APK 내부 구조 비교**

```
안드로이드 앱 (APK)
│
├── 일반 코드
│   ├── Utils.java             (개발자가 자유롭게 사용)
│   ├── Helper.java
│   └── DatabaseManager.java
│
└── 컴포넌트 (시스템이 관리)
    ├── MainActivity.java      (Activity - 화면)
    ├── MusicService.java      (Service - 백그라운드)
    ├── AlarmReceiver.java     (Receiver - 알림)
    └── ContactsProvider.java  (Provider - 데이터 공유)

※ 모든 코드는 최종적으로 classes.dex 파일 1개에 통합된다.
```

**코드 비교**

```kotlin
// 일반 코드 사용
val utils = Utils()   // 개발자가 직접 생성
utils.doSomething()   // 자유롭게 호출

// 컴포넌트 사용
val intent = Intent(this, MainActivity::class.java)
startActivity(intent) // 시스템에 요청
```

## 2.2 Activity

### 화면(UI) 역할

Activity는 사용자에게 보이는 화면을 담당하는 컴포넌트다.

**클래스 구조**

```kotlin
class MainActivity : AppCompatActivity() {
    // AppCompatActivity를 상속받음
    // AppCompatActivity는 Activity의 하위 클래스
}
```

**특징**
- 하나의 Activity는 하나의 화면을 의미한다.
- UI 요소(버튼, 텍스트 등)를 포함한다.
- 사용자와 상호작용한다.


### 생명주기

Activity는 시스템이 관리하는 생명주기(Lifecycle)를 가진다.

**생명주기 흐름**

```
onCreate() → onStart() → onResume()
                  ↓
          [Activity 실행 중]
                  ↓
onPause() → onStop() → onDestroy()
```

**생명주기 메서드**

| 메서드           | 호출 시점          | 역할            |
| ------------- | -------------- | ------------- |
| `onCreate()`  | Activity 생성    | 초기화 (레이아웃 설정) |
| `onStart()`   | 화면 보이기 시작      | 리소스 준비        |
| `onResume()`  | 사용자 상호작용 시작    | 포그라운드 실행      |
| `onPause()`   | 다른 Activity 전환 | 일시 정지, 데이터 저장 |
| `onStop()`    | 화면 완전히 가려짐     | 리소스 해제        |
| `onDestroy()` | Activity 종료    | 최종 정리         |

**AndroidManifest.xml 등록**

```xml
<activity android:name=".MainActivity">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>
```

## 2.3 Service

### 백그라운드 작업

Service는 화면 없이 백그라운드에서 작업을 수행하는 컴포넌트다.

**클래스 구조**

```kotlin
class MusicService : Service() {
    // Service 클래스를 상속받음

    override fun onBind(intent: Intent): IBinder? {
        return null
    }
}
```

**특징**
- UI가 없다.
- 백그라운드 작업을 처리한다.

**AndroidManifest.xml 등록**

```xml
<service
    android:name=".MusicService"
    android:exported="false" />
```

## 2.4 Broadcast Receiver

### 시스템 이벤트 수신

Broadcast Receiver는 시스템 이벤트를 수신하는 컴포넌트다.

**클래스 구조**

```kotlin
class BatteryReceiver : BroadcastReceiver() {
    // BroadcastReceiver 클래스를 상속받음

    override fun onReceive(context: Context, intent: Intent) {
        // 이벤트 수신 시 실행
    }
}
```

**특징**
- UI가 없다.
- 짧은 작업만 수행한다 (10초 이내).
- 시스템 이벤트를 감지한다.

**수신 가능한 이벤트**

| 이벤트     | Action                | Receiver 클래스 예시   |
| ------- | --------------------- | ----------------- |
| 부팅 완료   | `BOOT_COMPLETED`      | `BootReceiver`    |
| 배터리 부족  | `BATTERY_LOW`         | `BatteryReceiver` |
| 네트워크 변경 | `CONNECTIVITY_CHANGE` | `NetworkReceiver` |
| SMS 수신  | `SMS_RECEIVED`        | `SmsReceiver`     |

**Manifest 등록**

```xml
<receiver
    android:name=".BatteryReceiver"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BATTERY_LOW" />
    </intent-filter>
</receiver>
```

## 2.5 Content Provider

### 앱 간 데이터 공유

Content Provider는 앱 간 데이터를 공유하는 컴포넌트다.

**클래스 구조**

```kotlin
class MyProvider : ContentProvider() {
    // ContentProvider 클래스를 상속받음

    override fun query(...): Cursor? {
        // 데이터 조회
    }
}
```

**특징**
- 데이터베이스, 파일 등을 다른 앱과 공유한다.
- URI 기반으로 접근한다.
- 권한 제어가 가능하다.

**실생활 예시**

| Provider 클래스       | 제공 데이터  | URI                               |
| ------------------ | ------- | --------------------------------- |
| `ContactsProvider` | 연락처 정보  | `content://contacts/people`       |
| `MediaProvider`    | 사진, 동영상 | `content://media/external/images` |
| `CalendarProvider` | 캘린더 일정  | `content://calendar/events`       |

### URI 기반 접근

**URI 구조**

```
content://com.example.provider/users/1
↑              ↑                  ↑     ↑
스킴        Authority            경로   ID
```

**AndroidManifest.xml 등록**

```xml
<provider
    android:name=".MyProvider"
    android:authorities="com.example.provider"
    android:exported="true"
    android:permission="com.example.READ_DATA" />
```

**Content Provider 시스템 동작 순서**

```
앱 B → content://com.example.provider/users/1
        ↓
Content Provider (MyProvider 클래스)
        ↓
SQLite 데이터베이스 (/data/data/com.example.app/databases/users.db)
        ↓
users 테이블에서 id=1인 데이터 가져오기
        ↓
결과: {id: 1, name: "홍길동"}
 ↓
보안 취약점: {id: n, name: "admin,user"} 파라미터 값 조정
```

## 2.6 Intent를 통한 통신

### Intent란?

Intent는 컴포넌트 간 통신을 위한 메시지 객체다. Intent는 처음에 시스템에 전달되고, 시스템이 Intent를 분석해서 최종 목적지 컴포넌트로 전달하고 실행한다.

**역할**
- Activity를 시작한다.
- Service를 시작한다.
- Broadcast를 전송한다.

### 명시적 Intent

특정 컴포넌트 클래스를 직접 지정한다.

```kotlin
// MainActivity에서 DetailActivity로 이동
val intent = Intent(this, DetailActivity::class.java)
intent.putExtra("userId", 123)
startActivity(intent)
```

### 암시적 Intent

Action만 지정하고 시스템이 적절한 앱을 선택하게 한다.

```kotlin
// 웹 브라우저 열기
val intent = Intent(Intent.ACTION_VIEW, Uri.parse("https://google.com"))
startActivity(intent)

// 전화 걸기
val intent = Intent(Intent.ACTION_DIAL, Uri.parse("tel:01012345678"))
startActivity(intent)
```

# 3. Android Runtime (ART)

## 3.1 ART 개요

### 가상 머신 역할

Android Runtime (ART)은 Java/Kotlin 코드를 실행하는 가상 머신이다.

**가상 머신이란?**
- 실제 하드웨어가 아닌 소프트웨어로 만든 가상의 실행 환경이다.
- Java/Kotlin 바이트코드를 기계어로 번역해서 실행한다.
- 운영체제와 앱 사이의 중간 계층 역할을 한다.

**ART의 위치**

```
┌───────────────────────────┐
│    Applications (앱)       │
├───────────────────────────┤
│   Java API Framework       │
├───────────────────────────┤
│ Android Runtime (ART) ← 여기! │
├───────────────────────────┤
│           HAL              │
├───────────────────────────┤
│       Linux Kernel         │
└───────────────────────────┘
```

### 앱 실행 환경

**ART의 주요 역할**

| 역할     | 설명                           |
| ------ | ---------------------------- |
| 코드 실행  | Java/Kotlin 바이트코드(DEX)를 실행한다 |
| 메모리 관리 | 가비지 컬렉션(GC)으로 메모리를 자동 회수한다   |
| 앱 격리   | 각 앱마다 독립된 가상 머신 인스턴스를 제공한다   |
| 성능 최적화 | JIT/AOT 컴파일로 실행 속도를 향상시킨다    |

**앱별 독립 실행**

```
카카오톡 앱 (PID: 1234)
   ↓
ART 인스턴스 1 (독립된 가상 머신)
   ↓
독립된 메모리 공간

인스타그램 앱 (PID: 1235)
   ↓
ART 인스턴스 2 (독립된 가상 머신)
   ↓
독립된 메모리 공간
```

## 3.2 Dalvik VM vs ART

### JIT vs AOT 컴파일

**Dalvik VM: JIT (Just-In-Time)**
- 실행 시점에 코드를 번역한다.
- 앱을 실행할 때마다 번역 작업이 필요하다.
- 설치는 빠르지만 실행은 느리다.

**JIT 동작 방식**

```
앱 실행 요청
   ↓
DEX 파일 로드
   ↓
실행하면서 실시간으로 번역 (JIT)
   ↓
기계어 실행
```

**ART: AOT (Ahead-Of-Time) 컴파일**
- 설치 시점에 미리 코드를 번역한다.
- 앱 실행 시 이미 번역된 코드를 사용한다.
- 설치는 느리지만 실행은 빠르다.

**AOT 동작 방식**

```
앱 설치 요청
   ↓
DEX 파일 → OAT 파일로 사전 컴파일 (AOT)
   ↓
설치 완료
   ↓
앱 실행 시 이미 번역된 OAT 파일 바로 실행
```

### 성능 차이

**Dalvik (JIT) 특징**

| 장점          | 단점            |
| ----------- | ------------- |
| 빠른 앱 설치     | 느린 앱 실행 속도    |
| 적은 저장 공간 사용 | 높은 배터리 소모     |
|             | 실행할 때마다 번역 작업 |

**ART (AOT) 특징**

| 장점                 | 단점          |
| ------------------ | ----------- |
| 빠른 앱 실행 속도 (2배 이상) | 느린 앱 설치     |
| 낮은 배터리 소모          | 많은 저장 공간 사용 |
| 부드러운 UI            |             |
