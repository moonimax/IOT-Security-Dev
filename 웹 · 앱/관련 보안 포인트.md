## 보안 포인트 1

- **UID 격리** : 안드로이드는 앱마다 고유한 Linux UID를 부여해서 프로세스와 파일 시스템 수준에서 서로 격리한다. 루팅되지 않은 정상 기기에서는 앱 A가 앱 B의 데이터 디렉토리(`/data/data/com.b.app/`)에 직접 접근할 수 없다.
- **APK 서명 검증(META-INF)**: `META-INF/`에는 `MANIFEST.MF`, `CERT.SF`, `CERT.RSA`(또는 `.DSA`) 파일이 들어있고, 설치 시 이 서명을 기준으로 앱 무결성과 업데이트 가능 여부(동일 서명 여부)를 검증한다. 서명이 다르면 같은 패키지명이라도 업데이트 설치가 거부된다.
- **exported 속성 점검**: `android:exported="true"`인 Activity/Service/Receiver/Provider는 다른 앱(또는 악성 앱)이 직접 호출할 수 있으므로, 실제로 외부 노출이 필요한 컴포넌트인지 점검 대상이 된다.
- **AndroidManifest.xml 정적 분석**: `apktool`, `jadx` 등으로 APK를 디컴파일해 Manifest와 권한 목록을 먼저 확인하는 것이 모의해킹의 기본 절차다.

## 보안 포인트 2

- **Activity 하이재킹 / 태스크 어피니티 공격**: exported된 Activity에 민감한 정보를 그대로 노출하면, 악성 앱이 해당 Activity를 직접 실행해 화면을 가로채거나 데이터를 탈취할 수 있다.
- **Service 취약점**: `exported="true"`인 Service는 외부 앱이 바인딩(`bindService`)해서 내부 로직을 호출할 수 있으므로, IPC(AIDL 등)로 노출되는 메서드에 권한 검증이 있는지 확인해야 한다.
- **Broadcast Receiver 스푸핑**: 암시적 브로드캐스트를 수신하는 Receiver는 다른 앱이 위조된 Intent를 보내 오작동을 유발할 수 있다. 민감한 브로드캐스트는 `android:permission` 또는 `LocalBroadcastManager`(또는 최신 방식인 명시적 브로드캐스트)로 제한하는 것이 안전하다.
- **Content Provider SQL 인젝션 / 경로 탐색**: `query()`, `insert()` 등에서 입력값을 그대로 SQL에 사용하면 SQL 인젝션이 발생할 수 있고, 파일 기반 Provider는 `../` 등을 이용한 경로 탐색(Path Traversal) 공격에 노출될 수 있다.
- **Intent 관련 취약점**: 명시적 Intent라도 `putExtra`에 담긴 데이터가 검증 없이 사용되면 위조된 값으로 로직을 변조할 수 있고, 대기 중인 `PendingIntent`를 잘못 설정하면 다른 앱이 이를 가로채 악용할 수 있다(Intent Redirection/Hijacking).

## 보안 포인트 3

- **ART 기반 리버싱**: DEX → OAT(네이티브 코드) 컴파일 구조 때문에, 설치된 앱을 분석할 때는 `.dex`(바이트코드 그대로)와 `.oat`/`.vdex`(사전 컴파일된 네이티브 코드) 두 형태를 모두 고려해야 한다.
- **메모리 보호**: ART의 가비지 컬렉션과 앱별 독립 가상 머신 인스턴스는 각 앱의 메모리 공간을 분리해서, 한 앱의 메모리 손상이 다른 앱으로 바로 전이되지 않도록 하는 안전장치 역할도 한다.
- **디버깅/루팅 탐지와의 연관성**: ART 프로세스는 `ptrace` 등으로 후킹(Frida 등 동적 분석 도구)될 수 있어서, 보안이 중요한 앱은 ART 레벨에서의 후킹 여부를 탐지하는 로직을 추가하기도 한다.
